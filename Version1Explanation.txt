What is my project about??
How can we build a backend that can continue accepting requests even when downstream processing or the database becomes slow?

Requirement:
• Accept events from clients.
• Store every event reliably.
• Avoid losing events if processing becomes slow.
• Decouple request handling from database operations.

FailSafe, which is an event-driven backend system that I'm building using Java, Spring Boot, Apache Kafka, and PostgreSQL.
---------------------------------------------------------------------------------------------------------------------------------------


Problem it solve!!

The idea behind this project is that modern systems receive thousands of requests simultaneously. If every request directly communicates with the database, the system becomes tightly coupled and difficult to scale. A temporary database slowdown can affect the entire application. I wanted to understand how production systems decouple request processing and handle high traffic reliably.

Q--Why it become tightly coupled??
Client
   ↓
Controller
   ↓
Service
   ↓
Database

Now imagine the database becomes slow.

The Service cannot continue until the database responds.

The Controller also waits.

The Client waits.

Everything depends on the database.

This is called tight coupling because every component is directly dependent on the next one.

Any slowdown propagates through the entire application.

Q--What is scaling??
Scalability is the ability of a system to continue performing efficiently even when the number of users or requests increases.

Example:

100 Requests/sec

↓

10,000 Requests/sec

If the application can still process requests efficiently by increasing resources, it is scalable.

There are two types:

Vertical Scaling

Increase CPU or RAM of the same server.

Horizontal Scaling

Add multiple servers.

Production systems generally prefer Horizontal Scaling.

Solution I am trying to build??

To solve this, I designed FailSafe as an asynchronous event-driven architecture. Instead of directly processing every request, the application first publishes the incoming event to Kafka. Kafka acts as a durable event stream, allowing producers and consumers to work independently.

↓

Processing Service

↓

MySQL

When a client sends a request, the controller validates it and passes it to the service layer. The service publishes the event using KafkaProducer. Kafka stores the event inside a topic. A consumer listens to that topic, processes the event independently, and finally persists it into PostgreSQL. This makes the producer and consumer loosely coupled and improves scalability.
